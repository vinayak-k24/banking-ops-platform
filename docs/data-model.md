# Data Model and Mock Data

All pages share one synthetic dataset. Static seed data lives in `backend/mock_data/*.json`, generated by `backend/scripts/generate_mock_data.py` (fixed random seed, so output is repeatable).

## Collections

| Collection | Key | Main fields | Seed records |
|---|---|---|---|
| systems | system_id | name, type, environment, health | 6 |
| database_metrics | snapshot_id | database_id, seq, day, allocated_gb, used_gb, timestamp | 7 |
| archival_jobs | job_id | database_id, target_table, status, duration_s, records_processed, last_error | 3 |
| queue_metrics | queue_id | backlog, arrival_rate_per_min, processing_rate_per_min, avg_wait_min | 2 |
| service_metrics | service_id | name, latency_ms, error_rate, availability, dependencies | 5 |
| incidents | incident_id | title, severity, service_id, status, owner, evidence | 2 |
| transactions | reference_id | source (LEDGER/SETTLEMENT), counter_reference, amount, status | 118 |
| reconciliation_exceptions | exception_id | reference_id, expected_amount, actual_amount, reason, status | 5 |
| compliance_controls | control_id | category, description, owner, status, evidence_refs, due_date | 5 |
| migration_modules | module_id | name, source/target language, stage, complexity, dependencies, test_status | 8 |
| mock_logs | log_id | component, severity, message, correlation_id, timestamp | 6 |
| agent_tasks | task_id | workflow, status, steps, context, result, approval_id | runtime |
| approvals | approval_id | task_id, action, parameters, required_role, decision, reviewer | runtime |
| audit_events | event_id | actor, action, target, outcome, related_task_id, details | runtime |
| migration_documents | document_id | file_name, source_type, size_bytes, storage_uri, status, page_count, embedding_method, plan_id | runtime |
| migration_chunks | chunk_id | document_id, index, page_start, page_end, text, embedding | runtime |
| migration_plans | plan_id | task_id, document_id, status, components, plan (phases, timeline), narrative, checks, warnings | runtime |

Uploaded files are stored in Cloud Storage under `gs://$GCS_BUCKET/migration/<document_id>/` when `GCS_BUCKET` is set, otherwise in `backend/uploads/` (gitignored).

Database snapshots are ordered by `seq`, not timestamp, because simulated actions add snapshots with wall-clock time.

## Seed scenario

- `DB2_MAIN`: 10,240 GB allocated, ~84.8% used, growing 120 GB/day → above the 80% warning threshold.
- Archival jobs: one completed, one in lock delay (deadlock errors), one delayed waiting on it.
- Archival queue: backlog 1,240 and growing (arrivals 42/min > processing 31/min).
- Payment API: latency and error rate above SLO, with connection-pool errors in logs.
- Reconciliation: 5 amount mismatches and 2 missing settlement records.
- Compliance: one control with a gap, one overdue.

Thresholds are configuration (`backend/config.py`), not real banking limits.

## Storage backends

| `STORE_BACKEND` | Behaviour |
|---|---|
| `memory` (default) | Loads JSON at startup into process memory. Resets on restart; not shared between Cloud Run instances. |
| `firestore` | Uses Firestore collections with the same names. Seed with `python scripts/seed_firestore.py --project <id>`. |

Regenerate data: `cd backend; python scripts/generate_mock_data.py`.
